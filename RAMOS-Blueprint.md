# RAM-OS — Life Operating System Blueprint (v0.1, simulation-ready)

**One line:** Run your life through your corporation. RAM Strategic Systems
is the operating frame; you are the operator; financial stability is the
primary objective the whole system serves.

## 0. Why this structure (grounded, not theory)

This blueprint is not invented. It stands on three established sources and
is deliberately hardened against the documented reasons these systems die:

- **Structure → PPV** (Pillars, Pipelines & Vaults). Pillars = life
  segments/departments; Pipelines = process flow from goal to task; Vaults
  = knowledge. Your corporate-department instinct is PPV.
- **The action loop → GTD** (Capture → Clarify → Organize → Reflect →
  Engage). Your "data dump → follow-up" is this loop.
- **Survival design → failure-mode research.** The consistent finding:
  systems fail from abandoned habits and over-engineering, not bad
  structure. Building the system becomes a way to avoid the work. Survival
  correlates with low friction + restartability, not sophistication.

**Success is not a percentage. Success = the system still being run in 90
days.** We measure that as *invariant resilience under simulation*
(Section 5–6), the same way we stress-tested Ovis Canem.

## 1. The objective

- **Primary objective:** financial stability.
- **The OS delivers all four jobs at once, because a company already does:**
  - Accountability = management
  - Clarity = one dashboard
  - Goal-drive = objectives
  - Whole-life view = the company view
- One structure, four jobs. Not a to-do app — the operating system of a
  one-person company.

## 2. The structure — three layers

### Layer A — Pillars (the 5 departments)

Each pillar has one objective and one health signal (green/yellow/red).
That's it — no elaborate dashboards.

| Pillar | Role | Objective (v0.1) | Health signal |
|---|---|---|---|
| Finance | The scoreboard | Stable runway + rising savings | Weeks of runway on hand |
| Revenue / Ops | Engine 1 | RAM + income producing now | $ booked this month |
| Growth | Engine 2 | Bigger income later (GTM, skills, network) | Applications / conversations live |
| Self | Keeps operator running | Energy, mind, creative | Did I train/create this week? Y/N |
| Admin | Keeps lights on | Home, daily systems, compliance | Anything overdue? Y/N |

**Alignment rule:** every task must trace to a pillar. If it advances no
pillar, it's cut or deprioritized.

### Layer B — Pipelines (how work flows)

One directional flow: **Capture → Task → Project → Pillar.** Detailed as
the operating loop in Section 3.

### Layer C — Vaults (reference/knowledge)

Static knowledge only: SOPs, client docs, notes, templates. **Separate
from action.** A vault answers "what do I know"; a pipeline answers "what
do I do next." Never mix them.

### CEO layer (you + strategic architect)

The weekly review. Sets the 1–3 priorities that override everything else.

## 3. The operating loop (your "data dump → follow-up" system)

Designed so it survives your worst day, not just your best one.

1. **CAPTURE** — under 10 seconds, zero decisions. One inbox. Everything
   dumps here unsorted — task, idea, expense, note. You never decide
   *anything* at capture time. This is the whole reason the system
   survives; if capture has friction, the system is dead.
2. **CLARIFY** — daily, ~5 minutes, batched. Process the inbox. Each item
   becomes exactly one of: a **Task** (tagged to a pillar, with a concrete
   next action), a **Vault note**, or **trash**. Inbox goes to empty.
   That's the only daily obligation.
3. **ENGAGE** — work from a SHORT list. Your daily driver is a "Today"
   list of ≤ 3 tasks pulled from the task list — never the inbox, never
   the whole system. You act from a short list, not from the machine.
4. **REVIEW** — weekly, under 20 minutes. The CEO meeting. Check each
   pillar's health signal. Clear inbox to zero. Set next week's 1–3
   priorities. Done.

**Design rule:** capture is frictionless, processing is batched, the daily
driver is short. Everything else is optional.

## 4. Rollout — spine first (non-negotiable)

Building all five pillars at once is the documented death of these
systems, and it's your named failure mode wearing a productivity costume.

- **Phase 1:** Finance + Revenue/Ops pillars + the capture loop. Nothing
  else. Run it until the habit holds (~2–3 weeks).
- **Phase 2:** Add Growth.
- **Phase 3:** Add Self + Admin.

"Build the habit before the system" was the single most-repeated finding
in the research. We obey it.

## 5. Invariants (what must always stay true)

These are the simulation targets. Each maps to a documented failure mode.

- **I1 — Frictionless capture.** Capture is always < 10 sec and requires
  zero decisions. *(Guards against: friction kills capture.)*
- **I2 — Restartability / no guilt.** A missed day is never a failure
  state. The system restarts from any point with no backlog penalty and
  no guilt. *(Guards against: guilt-on-miss → abandonment. This is the one
  that protects your pull-back pattern.)*
- **I3 — Building ≠ working.** Reorganizing or "improving" the system is
  never counted as productive output. Only pillar-advancing work counts.
  *(Guards against: over-engineering as procrastination — your top risk.)*
- **I4 — Pillar alignment.** Every task traces to a pillar; anything that
  doesn't is cut. *(PPV alignment.)*
- **I5 — Time caps.** Daily processing ≤ 5 min, weekly review ≤ 20 min. If
  either bloats, the system gets simplified — the human is never blamed.
  *(Guards against: maintenance overhead.)*
- **I6 — Single source of truth.** One inbox, one task list, one home
  (Obsidian / Markdown). No parallel systems. *(Guards against:
  fragmentation.)*

## 6. Simulation scenarios (run next)

Same method as Ovis Canem: throw each scenario at the system, check which
invariant holds or breaks, patch, re-run.

- **S1 — The 4-day fall-off.** You don't touch it for 4 days. Does it
  guilt you, pile a backlog, or get abandoned? → tests I2.
- **S2 — The anxious tinker.** High-stress day; you want to "improve the
  system." Does the structure let you rabbit-hole into building instead
  of doing? → tests I3.
- **S3 — Money lands.** UI + LongHorn hit. Does capture → Finance route
  allocation with no friction? → tests I1, I4.
- **S4 — Client says yes.** A RAM lead converts. Does it flow cleanly
  Capture → Revenue → project → tasks? → tests I4, I6.
- **S5 — Laptop dark.** Claw can't run for days. Does the OS still work
  pull-only from your phone? → tests interaction-model resilience.
- **S6 — Two pillars, one hour.** Finance work and a Growth deadline
  collide. Does the CEO/weekly-priority layer resolve it? → tests the
  goal-drive function.

**Scoring:** a system that holds all six invariants across all six
scenarios is one you'll still be running in 90 days. That — not a fake
percentage — is the success rate.

## 7. Build note (for Claude Code)

Build order mirrors the rollout: (1) the single Capture inbox, (2) the
Task list with pillar tags, (3) Finance + Revenue pillar pages with one
health signal each, (4) the weekly-review template. Everything as
Markdown in the Obsidian vault so it outlasts any tool. Do **not** build
Phases 2–3 until Phase 1's habit holds.
